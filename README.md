# Как это устроено

## Общая схема

```
                     ┌──────────────────────────────────────┐
                     │        Sunflower Land community       │
                     │       API (marketplaceActivity)        │
                     └────────────────────┬────────────────────┘
                                          │ HTTP GET, раз в
                                          │ POLL_INTERVAL_SECONDS
                                          ▼
┌───────────────────────────────────────────────────────────────┐
│  docker network: shared-net (та же, где у тебя Postgres "sfl")│
│                                                                 │
│   ┌───────────────┐        пишет строки        ┌────────────┐ │
│   │   collector    │ ───────────────────────────▶│  Postgres  │ │
│   │  (контейнер,   │                              │     sfl    │ │
│   │  restart:always)│                              │ (уже есть) │ │
│   └───────────────┘                              └─────┬──────┘ │
│                                                          │ читает │
│                                                          ▼        │
│                                                   ┌────────────┐ │
│                                                   │     api     │ │
│                                                   │  (FastAPI)  │ │
│                                                   └──────┬──────┘ │
│                                                          │ порт   │
│                                                          │ НЕ     │
│                                                          │ пробро-│
│                                                          │ шен на │
│                                                          │ хост   │
└───────────────────────────────────────────────────────────────┘
                                                          │
                                                          │ доступ только
                                                          │ по внутреннему
                                                          │ DNS-имени "api:8000"
                                                          ▼
                                          ┌───────────────────────────┐
                                          │  Любой другой контейнер,    │
                                          │  подключённый к shared-net  │
                                          │  (например, backend твоего  │
                                          │  сайта)                     │
                                          └───────────────────────────┘
```

## Кто что делает

**collector** — единственный, кто ходит во внешний интернет (к API
Sunflower Land). Раз в `POLL_INTERVAL_SECONDS` (по умолчанию 300 сек =
5 минут):
1. Берёт сегодняшнюю дату по UTC.
2. Делает один запрос `marketplaceActivity`.
3. Из 51 отслеживаемого ресурса (`resource_ids.json`) берёт метрики
   (`floor`, `low`, `high`, `latestSale`, `bestOffer`, `volume`,
   `trades`, `quantity`, ...) и пишет по одной строке на ресурс в
   таблицу `sfl_resource_prices`.
4. При первом запуске сам создаёт таблицу и индексы, если их ещё нет.

Он **не отдаёт никакой API наружу** — только пишет в БД.

**api** — единственный, кто читает из БД для отдачи наружу. Сам
ничего не опрашивает и не пишет. Простой FastAPI с ручками:

- `GET /health` — жив ли сервис
- `GET /resources` — список ресурсов, которые вообще отслеживаются
- `GET /prices/latest` — последняя цена по каждому ресурсу разом
- `GET /prices/{item_key}/latest` — последняя цена одного ресурса
- `GET /prices/{item_key}/history?hours=24` — история цены за N часов

## Почему API закрыт от внешнего мира

В `docker-compose.yml` у сервиса `api` **нет** секции `ports` — Docker
не публикует его порт 8000 на хост. Это значит:

- Он недоступен ни с твоего сайта из браузера напрямую (никакой
  `fetch("https://твой-домен/...")` не сработает — там просто нечего
  слушать снаружи).
- Он доступен только другим **контейнерам**, подключённым к той же
  сети `shared-net`, по имени сервиса: изнутри такого контейнера
  запрос будет выглядеть как `http://api:8000/prices/latest` — Docker
  сам резолвит имя `api` в адрес контейнера внутри сети.

**Практическое следствие для сайта:** если фронтенд сайта — это код,
исполняющийся в браузере пользователя, он не может напрямую сходить в
`api:8000` (браузер не в docker-сети). Значит между ними должен быть
твой собственный публичный backend/BFF-слой, который:
1. Подключён к той же `shared-net`.
2. Сам ходит внутри сети в `http://api:8000/...`.
3. Отдаёт результат наружу пользователю уже через свой публичный
   домен/reverse proxy — так, как ты обычно публикуешь остальные свои
   сервисы.

Если такого backend-слоя пока нет и нужен быстрый публичный доступ —
самый простой вариант: повесить на этот же сервис `api` reverse proxy
(тот, что уже используешь для других контейнеров), подключённый к
`shared-net`, вместо прямой публикации порта. Так `api` всё равно не
торчит в интернет напрямую, а весь внешний трафик идёт через прокси,
где можно добавить домен/HTTPS/rate-limit при необходимости.

## Проверка изнутри сети (без публикации порта)

Поскольку порт не пробрасывается, `curl localhost:8000` с хоста
работать не будет — это ожидаемо. Проверить работоспособность можно
из любого контейнера в той же сети, например прямо из `collector`:

```bash
docker compose exec collector python3 -c \
  "import urllib.request; print(urllib.request.urlopen('http://api:8000/health').read())"
```

или временным контейнером, подключённым к `shared-net`:

```bash
docker run --rm --network shared-net curlimages/curl \
  curl -s http://api:8000/prices/latest
```

## Почему именно так, а не иначе

- **Один опрос — много строк**: раз в 5 минут collector пишет ~51
  строку (по числу ресурсов), это ~15 тыс. строк/день — для Postgres
  тривиально, истории хватит на годы вперёд без чистки.
- **collector и api разделены**: у collector нет причин быть
  доступным снаружи (он ничего не отдаёт), у api нет причин ходить в
  интернет (он ничего не собирает) — каждый сервис делает ровно одну
  вещь, это упрощает и отладку, и безопасность (даже если один из
  контейнеров скомпрометирован, у него нет прав/возможностей второго).
- **Таблица создаётся сама**: не нужно помнить про ручные миграции при
  переезде на новый сервер — контейнер collector всегда доводит схему
  БД до нужного состояния при старте.
